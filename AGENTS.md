# Работа с PM English через Codex

Эти инструкции относятся ко всему репозиторию. Они нужны, чтобы разные сессии Codex, работающие с одним GitHub-репозиторием, передавали друг другу актуальный контекст через Git, а не через историю чата.

## С чего начинать каждую сессию

1. Прочитай [АРХИТЕКТУРА.md](АРХИТЕКТУРА.md): концепцию, текущую комплектацию, карту файлов и ограничения совместимости.
2. Прочитай начало [Изменения.md](Изменения.md), затем записи после своей последней известной ревизии. Проверь `git status`, текущую ветку и свежие коммиты; при работе с GitHub проверь актуальную целевую ветку и открытые PR.
3. Если продолжаешь незавершённую реализацию, прочитай соответствующий последний раздел [PROGRESS.md](PROGRESS.md). Старые разделы — история проверок, а не описание текущего релиза.
4. Открывай только относящиеся к задаче файлы и функции по карте архитектуры. Для поиска используй `rg`; `index.html` читай небольшими фрагментами. Не выводи весь HTML: в нём есть крупные встроенные изображения и старые определения данных.

Документы сокращают повторное исследование, но не заменяют проверку затрагиваемого кода. Если документация расходится с текущей веткой, установи фактическое поведение и исправь описание вместе с изменением.

## Обязательная фиксация каждого изменения

При изменении кода, контента, стилей, сохранения, настроек, тестов или документации:

- Добавь запись в **начало раздела записей `Изменения.md` в том же коммите или PR**, что и само изменение. Не оставляй это на следующую сессию. Для нескольких связанных коммитов одного PR можно уточнять одну запись; отдельные этапы с разным результатом описывай отдельно.
- Укажи фактическое время внесения изменения в UTC: `YYYY-MM-DD HH:MM:SS UTC`. Отличай его от времени публикации. Время публикации добавляй только после подтверждённого deployment. Исторические даты бери из Git, а не из предположений.
- Опиши: что и зачем изменено; треки/главы/этапы; затронутые файлы; влияние на сохранение, ID, XP и открытие глав; выполненные проверки и ограничения; что осталось сделать. Для незатронутого укажи «не менялось» или «не применимо».
- Добавь известную ссылку на PR/коммит. Для ещё не опубликованного изменения укажи базовую ревизию и ветку: не выдумывай будущий SHA и не создавай отдельный коммит только ради ссылки на самого себя. Git хранит связь записи с её коммитом.
- Обнови `АРХИТЕКТУРА.md`, если изменились концепция, состав треков/заданий, связи модулей, данные, сохранение, зависимости, сборка, публикация или существенный контракт интерфейса. Архитектура описывает **текущее состояние**, журнал — **хронологию**.
- В продолжительных задачах обновляй `PROGRESS.md` после реализации и проверки: текущий этап, факты, оставшаяся работа. Итог переноси в журнал, не заставляя следующего агента восстанавливать результат из всех старых отчётов.

Запись должна быть понятна без чата: «исправлено по просьбе пользователя» недостаточно. Используй шаблон в журнале. Не записывай секреты, токены, личные данные и непроверенные заявления об успешных тестах или публикации.

## Несколько сессий и веток

- Веди работу в отдельной ветке; сохраняй существующие чужие изменения и записи.
- Перед завершением сверь свежую целевую ветку. При конфликте журналов сохрани обе записи и отсортируй по времени; не заменяй весь файл своей копией.
- Если после слияния изменился описанный результат или проверка, уточни запись и архитектуру. Не объявляй локальную реализацию опубликованной.
- В итоговом ответе укажи результат, проверки и ссылку на PR либо коммит. Если часть работы не завершена, запиши её в журнал и `PROGRESS.md`.

## Контракты приложения

- Не меняй стабильные case/task ID, `PLAN`, максимумы очков, storage keys, `RESET_TAG`, авторизацию и правила открытия глав без необходимости в текущей задаче. Их изменение требует явного описания совместимости и проверки старого прогресса.
- `career-content.js` генерируется из `content/` скриптом `scripts/build-career.cjs`. Меняй источники и регенерируй; прочие файлы `*practice-data.js` редактируются как авторские данные.
- Повторяющиеся case ID в разных треках нормальны. Поиск встроенного задания обязан учитывать трек, режим и реальное место в `PLAN`.
- Переиспользуй обработчики `select`, `order`, `match`. Не смешивай Additional с очками основной карьеры. Не пересчитывай уже выданные XP и пороги для действующих игроков.
- Сохраняй порядок материалов и стабильную перестановку ответов внутри попытки. При изменении подключаемого JS/CSS проверь версионные URL для браузерного кеша.
- Выбирай проверки по изменению из [tests/README.md](tests/README.md). Для правок только Markdown достаточно сверки фактов, ссылок и diff; не запускай весь игровой набор без причины.

## Что здесь означает «автоматически»

Codex подхватывает корневой `AGENTS.md` как инструкции репозитория и должен обновлять журнал во время работы. Эти файлы не являются Git-hook или серверным сборщиком событий: ручной push или инструмент, не читающий `AGENTS.md`, сам по себе не создаёт осмысленную запись. Общая память между сессиями появляется после сохранения документов в Git и получения актуальной ветки.
